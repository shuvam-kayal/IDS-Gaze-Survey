# Project-wide integration freeze

Status: frozen technical decisions for implementation planning

Date: 2026-10-12

This document is the integration authority for decisions that cross the four
workstreams. It supplements, but does not replace, the versioned JSON Schemas
under `contracts/schemas/`. Existing product requirements and the A-AF feature
checklist remain unchanged.

Each decision is classified as one of:

- **Frozen technical decision**: implementation may proceed against it.
- **Operational privacy default**: use this default for engineering and
  synthetic tests; legal, ethics, and institutional review may require a
  stricter rule before real collection.
- **Deferred enhancement**: intentionally not needed for the current release.

## 1. Identity and relationships

| Entity | Canonical identifier | Generated by | Notes |
|---|---|---|---|
| Experience | `experience_id` | P2 control plane | Identifies the registered website/product, not a person. |
| Study | `study_id` | P2 control plane | A study belongs to one Experience and has immutable published config versions. |
| Participant | `participant_id` | Session/bootstrap service | Optional pseudonymous identifier; never a verified real-world identity. |
| Session | `session_id` | Session/bootstrap service after consent | One browser participation session; may contain multiple eligible Studies. |
| Trial | `trial_id` | P1 runtime | Carries trial lifecycle context in event payloads where applicable. |
| Question | `question_id` | P2 configuration | Stable identity within a versioned QuestionConfig. |
| Question response | `response_id` | P1 runtime | Generated for a submitted response; must retain question and version context. |
| Event | `(session_id, event_id)` | P1 runtime | `event_id` is stable across retries of the same logical event. |
| Gaze sample | `sample_id` | P3 gaze pipeline | Stable within a session/provider capture stream. |
| Feature record | `feature_record_id` | P3 feature engine | Identifies one versioned derived output. |
| Analysis | `analysis_id` | P4 analytics | Identifies one analysis result, never a raw telemetry record. |

`participant_id` is optional and pseudonymous. Direct identifiers, passwords,
raw answers, and arbitrary page text are not collected by generic telemetry.

### Multiple Studies

One Experience may have multiple active Studies. A Session may be assigned to
zero, one, or multiple Studies. P2 owns eligibility and assignment. P1
consumes the pinned assignment and the separate consolidated survey-plan
contract keyed by `session_id`. P3 stores the event's immutable `study_ids`
context and does not recalculate eligibility. The survey-plan contract is
[`contracts/schemas/survey-plan.v1.schema.json`](../../contracts/schemas/survey-plan.v1.schema.json);
it is presented once at end of session and may cover multiple Study IDs.

The existing `EventEnvelope` remains unchanged: its `study_ids` array may
contain multiple IDs. A P3 `FeatureRecord` remains study-scoped because its
frozen schema has one `study_id`; P3 emits one record per applicable Study,
unless a future versioned contract explicitly defines a multi-study aggregate.

### Configuration versions

Published Experience, Study, AOI, and Question configurations are immutable.
Running Sessions retain the exact version identifiers received in bootstrap.
Editing a draft never changes the meaning of a running Session.

## 2. Event identity, validation, and idempotency

### Frozen technical decisions

1. The durable event identity is `(session_id, event_id)`.
2. No cross-session deduplication is performed.
3. Deduplication is checked before inserting a new event row, inside the same
   database transaction as the insert.
4. An exact retry has the same identity and an identical canonical payload.
5. An exact retry is acknowledged as a duplicate and does not create another
   row or derived processing job.
6. Reusing the same identity with a different payload, event type, context,
   or `occurred_at` is an identity conflict and is rejected with HTTP 409.
7. Validation failures are rejected before persistence with HTTP 422 and a
   stable machine-readable error code.
8. Unknown major schema versions are rejected. The current accepted version
   is `1.0.0`.

The canonical comparison for duplicate detection is a deterministic JSON
serialization of the complete EventEnvelope with object keys sorted and no
insignificant whitespace. The stored event row also retains a SHA-256
fingerprint for efficient comparison and audit-safe diagnostics.

The existing Slice 1 helper already uses `(session_id, event_id)` for local
batch deduplication and rejects conflicting duplicates. Durable persistence
extends that same rule across requests; it does not change the frozen
EventEnvelope schema.

## 3. Time and ordering

### Frozen technical decisions

- `occurred_at` is the client-observed event occurrence time in UTC RFC 3339.
- A timezone offset is required and must represent UTC (`Z` or `+00:00`).
- `ingested_at` is generated by the server when a new event is accepted. It is
  also UTC RFC 3339 in API output and timezone-aware UTC in storage. An exact
  retry returns the original stored `ingested_at`; it does not receive a new
  retry-arrival timestamp.
- `occurred_at` describes event meaning; `ingested_at` describes arrival.
- Events are accepted when valid even if they arrive late or out of order.
- Ingestion order never changes event meaning and is not used as a substitute
  for `occurred_at`.
- Retrieval order is deterministic: `occurred_at ASC`, then `ingested_at ASC`,
  then `event_id ASC`.
- Equal timestamps are therefore stable without relying on database row order.
- Invalid, naive, non-UTC, or unparsable timestamps are rejected.
- Clock skew is retained as a data-quality condition when the timestamp is
  still valid; the server does not rewrite client occurrence time.
- No streaming watermark is introduced in this release.

Late events that arrive after a FeatureRecord was generated mark the relevant
derived processing scope stale. They do not mutate the original event or
silently alter an already stored FeatureRecord.

## 4. Persistence architecture

### Frozen technical decision

Use PostgreSQL 16, SQLAlchemy 2.x, psycopg 3, and Alembic.

Rationale:

- PostgreSQL is already the repository's Docker Compose database.
- SQLAlchemy fits the existing Python backend and provides explicit
  transactions and repository boundaries.
- psycopg 3 is the current PostgreSQL driver family for Python.
- Alembic provides versioned, reviewable migrations.
- SQLite would hide PostgreSQL types, transaction behavior, and indexing
  differences; it is not an acceptable substitute.
- No second ORM, database, or migration framework may be introduced.

### Boundaries

- `services/telemetry/`: P3-owned validation, repositories, persistence,
  deduplication, retrieval, retention, and processing lifecycle.
- `services/gaze_engine/`: P3-owned provider boundary and canonical gaze
  persistence integration.
- `services/feature_engine/`: P3-owned feature generation and derived-record
  repositories.
- `services/api/app.py`: shared API wiring; changes require integrator and
  affected-owner review.
- `database/`: shared migration path; the integrator owns migration execution
  conventions, while P3 owns the telemetry model requirements.

### Transaction conventions

- Validate before opening a write transaction where possible.
- Within the write transaction, check the unique event identity, compare an
  existing fingerprint, and insert only when new.
- Commit event insertion and its processing-state enqueue atomically.
- Roll back the entire transaction on an unexpected persistence failure.
- Never log raw payloads, answers, frames, tokens, or provider objects.

### Configuration

- `DATABASE_URL` is the only application database connection setting.
- Development uses the existing Compose PostgreSQL service.
- Tests use a PostgreSQL database/schema created for the test run, not SQLite.
- Migration commands are run through Alembic after the migration system is
  added by the integrator.
- Synthetic fixtures are inserted through test repositories or explicit seed
  helpers; production startup does not silently seed research data.

## 5. Persisted records and processing lifecycle

### Persisted records

| Record | Persisted? | Owner | Timing |
|---|---:|---|---|
| Validated raw EventEnvelope metadata/payload | Yes | P3 | Immediately after idempotent acceptance |
| Server ingestion metadata | Yes | P3 | With the event transaction |
| Raw webcam video/frames | No by default | None | Never persisted in the platform pipeline |
| Canonical GazeRecord | Yes, subject to retention | P3 | After provider normalization |
| FeatureRecord | Yes, subject to retention | P3 | After successful deterministic generation |
| AnalysisRequest/AnalysisResult | Yes, subject to retention | P4 | Through the analytics workflow |

Raw gaze predictions are distinguishable from raw video: a GazeRecord stores
normalized measurements and quality metadata, not camera frames.

### Session and processing states

P3 processing state is separate from participant consent state:

`open -> finalizing -> complete`

An incomplete session may end as `partial`; a failed processing attempt is
`failed`; a deletion request ends the P3 lifecycle as `deleted` after required
records are removed. A session can be `partial` and still produce a valid
non-gaze FeatureRecord from the events available.

### Derived processing idempotency

The derived processing identity is:

`(session_id, study_id, feature_set_version, window_start, window_end)`

The processing repository additionally records an implementation/algorithm
version and input fingerprint. Repeating the same job with the same input
fingerprint returns the existing completed output. A changed fingerprint
creates a new processing attempt and does not overwrite history silently.

Late events mark matching completed scopes stale and enqueue recomputation.
The latest successful record is selected for ordinary retrieval; historical
attempts remain available to authorized operational tooling until retention
deletes them.

## 6. API contract freeze

The current `/v1/events` endpoint is still a scaffold and returns
`persisted: false`. The following is the target v1 behavior for the
coordinated persistence change. It must be implemented in `services/api/app.py`
only with affected-owner review.

### Request

`POST /v1/events` accepts the existing `EventEnvelope` v1 schema without
adding `ingested_at` to the client payload.

### New event response — HTTP 202

```json
{
  "schema_version": "1.0.0",
  "event_id": "evt-demo-0001",
  "status": "accepted",
  "duplicate": false,
  "ingested_at": "2026-01-01T10:00:03Z"
}
```

### Exact retry response — HTTP 200

```json
{
  "schema_version": "1.0.0",
  "event_id": "evt-demo-0001",
  "status": "duplicate",
  "duplicate": true,
  "ingested_at": "2026-01-01T10:00:03Z"
}
```

The response contract enforces the accepted/duplicate pairing and UTC
timestamp pattern in
[`contracts/schemas/event-ingestion-response.v1.schema.json`](../../contracts/schemas/event-ingestion-response.v1.schema.json).

### Validation error — HTTP 422

```json
{
  "schema_version": "1.0.0",
  "error": {
    "code": "invalid_event",
    "message": "occurred_at must include a UTC offset"
  }
}
```

### Identity conflict — HTTP 409

```json
{
  "schema_version": "1.0.0",
  "error": {
    "code": "event_identity_conflict",
    "message": "event_id is already used with different content"
  }
}
```

Error messages must not include raw payloads. The API may include opaque
`session_id` and `event_id` in structured diagnostic fields when authorization
allows it.

### Retrieval

The target P3 retrieval interface is an internal repository/service boundary
first. Any public route must be versioned and reviewed with P4 before adding
it. Retrieval is scoped by `session_id` and optionally `study_id`, uses the
deterministic ordering in Section 3, and requires cursor pagination for
unbounded result sets. It never returns raw video.

### Authentication boundary

Authentication and researcher authorization are P2/integrator concerns. P3
repositories enforce scope inputs but do not invent user roles. Participant
ingestion receives only the minimum session-scoped context required by the
approved API.

### Withdrawal/deletion request

The deletion operation is an authorized, idempotent service operation, not a
participant-facing raw SQL action. It returns a processing status and a
verification result. Its route and authorization integration require P2 and
integrator review.

## 7. Retention, withdrawal, and deletion

These are conservative engineering defaults, not legal or ethics approval.

### Operational privacy defaults

- Raw event payloads: 30 days after session closure.
- Canonical gaze records: 30 days after session closure.
- FeatureRecords: 90 days after session closure.
- Analysis results and reports: 90 days after creation.
- Participant-linked operational records: no longer than the related data.
- Aggregate infrastructure counters without session/participant linkage: 30
  days unless operations requires less.
- No raw video or frames are retained by default.

Before real collection, the project must obtain institutional/legal/ethics
review of purpose, consent language, retention, sharing, backup expiry, and
deletion guarantees. Local synthetic fixtures are not blocked by that review.

### Withdrawal and deletion behavior

Withdrawal stops new camera and research collection through P1. It marks the
session closed for P3 processing and starts deletion according to the approved
study policy. A deletion operation removes raw event payloads, canonical gaze,
FeatureRecords, derived caches, and linked AnalysisResults/reports that depend
on the deleted scope. It is retried until verification succeeds.

Only non-identifying operational counters may remain, and they must not retain
session IDs, participant IDs, raw payloads, answers, gaze coordinates, or
provider objects. Audit logs retain action type, actor role, target class,
timestamp, outcome, and a non-reversible operation ID, not deleted payloads.

Deletion tests verify both the primary rows and dependent records, repeat the
operation safely, and confirm that retrieval returns no deleted research data.

## 8. FeatureRecord and missingness semantics

The existing frozen modality values are retained:

- `gaze_and_non_gaze` means both gaze and non-gaze features are present or
  eligible for the record.
- `non_gaze_only` means gaze is unavailable, not collected, invalid, or not
  permitted and non-gaze features remain usable.

The existing `quality.missingness` array carries reason codes. Standard codes
are:

`gaze.permission_denied`, `gaze.camera_unavailable`,
`gaze.capture_interrupted`, `gaze.consent_withdrawn`,
`gaze.calibration_incomplete`, `gaze.low_quality`, `gaze.provider_failure`,
`gaze.not_collected_by_policy`, and `gaze.no_samples`.

Missing, null, absent, invalid, and measured zero remain distinct. No gaze
feature is filled with numeric zero because a camera was denied. Slice 1's
`non_gaze_only` fixtures remain valid without migration.

Every FeatureRecord includes the existing `feature_set_version`, configuration
versions where known, modality, quality, source-event count, and deterministic
feature values. Additional provenance belongs in the internal processing
metadata until a versioned schema change is approved.

## 9. Browser-to-gaze-provider boundary

- P1 owns research consent, browser permission, camera tracks, visible status,
  stop/withdrawal behavior, and participant-facing lifecycle.
- P3 owns provider selection, provider-specific adapter code, normalization,
  quality interpretation, and canonical GazeRecord semantics.
- P1 supplies a consented camera stream and page/AOI geometry snapshots through
  a narrow internal bridge. P1 does not import provider-native types. The
  bridge payload is the machine-readable
  [`ProviderSample`](../../contracts/schemas/provider-sample.v1.schema.json)
  contract: `provider`, `provider_version`, `sample_id`, monotonic
  `capture_time_ms`, UTC `occurred_at`, nullable viewport pixel `x_px`/`y_px`,
  `valid`, and bounded `quality.confidence` plus `quality.flags`.
- The lifecycle interface is `ProviderAdapter.start(input)` followed by
  `ProviderAdapter.stop()`. `input` contains the `session_id`, consented
  browser `MediaStream`, initial `GeometrySnapshot`, an `on_sample` callback,
  and an `on_status(status, reason?)` callback. Status values are
  `initializing`, `ready`, `unavailable`, and `stopped`. P1 calls `start` only
  after consent and calls `stop` on denial, withdrawal, teardown, or expiry.
  The corresponding TypeScript interfaces are in
  [`contracts/typescript/src/index.ts`](../../contracts/typescript/src/index.ts).
- The P3 adapter may execute in browser JavaScript when the selected provider
  requires it. Its provider-specific implementation remains P3-owned even if
  the artifact is bundled for the participant runtime.
- The adapter emits an internal `ProviderSample` matching the schema above.
- P3 converts ProviderSample to canonical `GazeRecord` before persistence or
  feature computation. Provider-native objects never enter canonical schemas.
- Browser capture time uses a monotonic clock for interval calculations and a
  UTC occurrence timestamp for cross-system records. Server `ingested_at` is
  separate.
- Provider initialization failure produces a reason-coded non-gaze path.

This boundary keeps a future provider replaceable without changing P1's
consent UX or P4's FeatureRecord consumer.

## 10. AOI, fixation, and metric baseline

### Coordinate and geometry rules

- Canonical gaze coordinates are `viewport_normalized` in `[0, 1]`.
- Origin is the top-left of the visible viewport; x increases rightward and y
  increases downward.
- P1 resolves live AOI rectangles in the same viewport coordinate space and
  emits a [`GeometrySnapshot`](../../contracts/schemas/geometry-snapshot.v1.schema.json)
  when layout, scroll, resize, zoom, or reflow changes. The snapshot carries
  `snapshot_id`, `session_id`, UTC `captured_at`, `aoi_set_version`, viewport
  width/height, scroll offsets, zoom, and timestamp-independent AOI rectangles
  in viewport pixels.
- P2 owns AOI definitions and `aoi_set_version`; P1 owns live geometry;
  P3 owns timestamped mapping.
- A rectangle uses left/top inclusive and right/bottom exclusive boundaries.
- Geometry rectangles must satisfy `right_px > left_px` and
  `bottom_px > top_px`; invalid rectangles are excluded from mapping and do
  not cause a sample to be assigned to a guessed AOI.
- Overlapping AOIs select the highest numeric `priority`; equal priorities
  tie-break by lexicographically smallest `aoi_id`.
- Samples with no valid geometry map to `aoi.unresolved`, never to a guessed
  AOI.

### Deterministic baseline algorithms

The first reusable baseline is `feature_algorithm_version = gaze-baseline-1`:

- Valid samples require valid coordinates and provider quality that has not
  been flagged unusable.
- A gap over 200 ms splits a trace.
- Fixations use a dispersion-duration rule over normalized viewport
  coordinates: at least 3 valid samples spanning at least 100 ms and with
  `max(x)-min(x) <= 0.05` and `max(y)-min(y) <= 0.05`.
- Samples crossing a gap or invalid run do not bridge fixations.
- TTFF is elapsed milliseconds from the pinned trial/exposure start event to
  the first qualifying fixation in the requested AOI.
- Dwell is the sum of qualifying fixation durations assigned to an AOI;
  invalid gaps are excluded, not interpolated.
- A revisit is a new qualifying fixation in the same AOI after at least one
  qualifying fixation in another AOI or an unresolved interval.
- A transition is the ordered pair of consecutive resolved AOIs.
- Scan path is the ordered AOI sequence after consecutive duplicates are
  collapsed.
- Entropy is Shannon entropy base 2 over AOI dwell shares. It is null with a
  reason code when fewer than two valid AOI observations exist.
- Every metric records units, denominator, time window, AOI/config versions,
  algorithm version, and missingness/quality context.

These are operational measurement definitions, not claims of scientific
validity. P4 must report limitations and sample quality.

## 11. Ownership and integration sequence

- P1: participant SDK, consent/camera lifecycle, trials, surveys, interactions,
  live AOI geometry, event buffering, and the narrow gaze bridge.
- P2: researcher console, roles, Experience/Study configuration, eligibility,
  AOI/question authoring, immutable versions, and bootstrap/config APIs.
- P3: telemetry validation/persistence, provider adapter, canonical gaze,
  quality, fixation/AOI mapping, gaze/non-gaze features, FeatureRecords, and
  telemetry deletion/retention implementation.
- P4: statistics, ML, evaluation, modality-aware analysis, visualizations,
  reports, and recommendations.
- Integrator/shared owners: API wiring, root manifests, Docker/Compose,
  migrations, CI, shared schemas, and shared contract tests.

Implementation order:

1. M0: this freeze and contract review.
2. M1: synthetic EventEnvelope -> non-gaze FeatureRecord -> AnalysisResult.
3. M2a: PostgreSQL/Alembic persistence and idempotent ingestion.
4. M2b: consented provider boundary, canonical gaze, quality, AOI mapping.
5. M3: multi-study assignment, consolidation, and config pinning.
6. M4: browser-to-result journeys, including denied/interrupted camera.
7. M5: retention, deletion, authorization, accessibility, performance, and
   deployment hardening.

## 12. Testing and reproducibility freeze

- Contract tests validate every schema and canonical example.
- Persistence tests run against PostgreSQL, never SQLite.
- Idempotency tests cover exact retries, conflicting identities, separate
  sessions, and transaction failure.
- Ordering tests cover equal timestamps, late events, and deterministic cursors.
- Deletion tests cover raw events, gaze, features, analysis outputs, retries,
  and verification.
- Camera-denied tests never access a webcam and must still produce non-gaze
  FeatureRecords.
- Provider tests use captured, de-identified structured provider output; live
  provider experiments are isolated and never part of the core CI suite.
- Feature tests use known-answer synthetic traces and fixed algorithm/version
  inputs.
- CI commands remain `ruff check .`, `pytest`, and `npm run typecheck`, with
  PostgreSQL service setup added when persistence implementation begins.
- No test requires live network access, a real participant, or a real webcam.

## 14. Change control

Any future change to identity, timestamp, modality, API response, database
schema, AOI semantics, provider boundary, or deletion behavior requires:

1. A rationale and affected A-AF IDs.
2. Producer and consumer owners.
3. Before/after examples.
4. Compatibility and migration notes.
5. Contract/schema/test updates in the same coordinated change or an approved
   migration series.
6. No new production dependency or provider without the P3 technical review
   and legal/license review where applicable.

The repository remains synthetic-only until privacy, security, ethics, and
operational release gates are separately satisfied.
